## Executive summary

**Verdict: still a strong architecture for hard scans / image-only books; needs a focused refresh for JSTOR born-digital scholarly volumes and for OpenCode local config hygiene. Not a rewrite.**

What you built (multi-engine → VLM merge, profiles, MCP, checkpoint/budget, 30 formats) remains ahead of “single converter dump to MD” for *bad scans*. Industry 2026 still converges on triage (text-layer cheap → Marker/Docling/MinerU layout → VLM/olmOCR only when needed). Your pipeline already implements that *shape*, but:

1. **Default MCP path is wrong for JSTOR FOTC** — `vlm_enabled=True` still re-renders + VLM-merges pages that already have extractable text → expensive and not what the pilot needed.
2. **FOTC pilot proved Marker `--disable_ocr` alone fails the publishable bar** on superscript footnotes and text-layer glyph garbage — problems the full VLM path *can* help with *selectively*, not whole-book.
3. **Local config is stale / specialized** — `config.yaml` is locked to Latin hagiography (`agreement_threshold: 1.0`, always-VLM); Marker lives only in `.marker-venv` and is missing from the main `uv` env; OpenCode MCP has Gemini+Mathpix secrets but **no Anthropic/xAI** for documented Claude/Grok fallbacks.
4. **~2 months since last commit** (2026-07-31 → 2026-10-07). Model IDs mostly still valid (`gemini-2.5-flash`, `claude-sonnet-5`), but docs should prefer **`claude-sonnet-5-5`** for new academic QA; Gemini free-tier capacity is tightening for new projects (Google pushing 3.x Flash family).

**Bottom line:** keep the pipeline; add a **JSTOR / text-layer profile + classifier**, fix MCP defaults/secrets, repair footnotes with PyMuPDF superscripts + selective page VLM, and stop treating Marker-only as gold.

### Dangerous default for JSTOR

In `page_processor.py`, if text extraction succeeds **and** `vlm_enabled` is True (MCP default), the pipeline **still renders PNG + VLM-merges**. For a 427-page FOTC volume that is ~427 API vision calls. Pilot correctly avoided this by calling Marker CLI directly with `--disable_ocr`.

### Ligature pitfall for Latin/patristics

Default `ligature_expand` NFKC + map turns `æ/œ` → `ae/oe` (`cælum` → `caelum`). Fine for modern English; **bad** for scholarly Latin/Greek-adjacent orthography. Academic / FOTC profiles should **disable** æ/œ expansion (keep fi/fl only, or skip ligature_expand).

## FOTC pilot findings (fold-in)

Pilot: FOTC 1 *Apostolic Fathers* (427 pp JSTOR merged PDF, real Type-1 text layer).

| Finding | Implication for pipeline |
|---|---|
| Superscript footnote anchors → bare digits / `l`/`I`; ~26 placeholder note defs | VLM academic prompt *asks* for `[^N]` but text-layer path never sees the page image unless VLM forced; need **PyMuPDF char flags / bbox superscripts** before/without full VLM |
| Multiple footnote series restarting at 1 on one page | Ordered footnote queue (pilot postprocess) must become a pipeline post-step, not ad-hoc |
| Glyph garbage *in text layer* (`tha~`, `phoemx`, `Histaria ccclesiastica`) | `--disable_ocr` preserves errors; need **garbage detector → selective page/span re-OCR or VLM** |
| Italics incomplete in body; better in Marker footnote spans | Prefer Marker layout for structure; VLM or span repair for emphasis recall |
| TOC → broken wide tables | Front-matter profile / classifier should skip table hallucination |
| Printed page ≠ JSTOR `/PageLabels` (often printed+1) | Page map is **outside** ocr-pipeline today — keep in Academic Research ingest; optional sidecar YAML |
| Full VLM whole-book wrong cost/quality trade for good text layers | New mode: `text_layer_first` + `vlm_on_fail` |

**Pilot did not invalidate the pipeline** — it showed Marker-only is insufficient for CMOS-grade FOTC, and blind whole-book VLM is the wrong fix.

## Industry compare (2025–2026 practice)

Sources: 2026 PDF→MD benchmarks (Docling / Marker / MinerU / olmOCR / Mathpix).

| Tool | Strength | Weakness for our JSTOR/FOTC case |
|---|---|---|
| **Marker** (+ Surya) | Fast batch layout→MD; good default; optional `--use_llm` | Footnote anchors weak; commercial-use weight caveats; multi-column/ref lists can scramble |
| **Docling** | Honest tables; MIT; structure for RAG | Weaker math/figures; not specialized for patristic notes |
| **MinerU** | Best tables/formulas in some benches | **Known to drop footnote bodies** while keeping markers — worse for FOTC |
| **olmOCR / VLM-per-page** | Hard scans | GPU cost; overkill for text-layer JSTOR |
| **Mathpix** | Fast non-Latin / math | Paid; already wired |
| **Your ocr-pipeline** | Multi-engine + profiled VLM + MCP + budget | Defaults/config ages; no JSTOR text-layer profile; no superscript repair |

**Industry consensus matches our triage:**  
born-digital simple → extract; complex born-digital → Marker/Docling; clean scans → OCRmyPDF/Marker; degraded → VLM/olmOCR. **Nobody serious force-OCRs good JSTOR text layers end-to-end.**

Your unique edge: **VLM merge across engines with academic prompts that already mention footnotes/italics/tables**. Gap: no page-type classifier, no selective repair loop, no scholarly footnote postprocess.

## Recommended routing (when to use what)

```
PDF arrive
  ├─ pdffonts / pdftotext smoke
  │    ├─ real fonts + sane extract  → LIGHT PATH
  │    │     Marker --disable_ocr --paginate_output
  │    │     OR ocr-pipeline with vlm_enabled=false + profile jstor_textlayer
  │    │     → postprocess (reflow, footnotes from superscripts, page_map)
  │    │     → QA garbage_rate / placeholder_count
  │    │          ├─ pass → index
  │    │          └─ fail pages → SELECTIVE PATH (below)
  │    └─ image-only / bad layer   → FULL PATH
  │          ocr-pipeline --profile academic|books|custom
  │          engines marker (+ mathpix if Greek/math)
  │          VLM gemini-2.5-flash; fallback claude-sonnet-5-5 for citations
  └─ AI glance (3–5 sample pages) sets profile: prose | notes-heavy | tables | verse | facing Greek
```

### JSTOR FOTC profile (proposed)

| Setting | Value |
|---|---|
| Name | `jstor_fotc` (user profile YAML) |
| Default engines | marker only (mathpix optional for Greek lemmas) |
| `vlm.enabled` | **false** by default |
| Selective VLM | only flagged pages (`garbage` / `unanchored_notes` / `low_italics_recall`) |
| Languages | `en,la,el` |
| Postprocess | dehyphenate + soft_hyphens + whitespace; **no æ/œ expand** |
| Output | markdown + page sidecar; strip JSTOR chrome |
| Cite | `FOTC {vol}:{page}`; `citation_profile: church-fathers` |

### Page-type classifier (“AI glance”)

Cheap Gemini Flash on 3–5 rendered pages (or Marker page samples) → labels:

- `prose_notes` (FOTC body)  
- `front_toc`  
- `apparatus_table`  
- `verse_or_liturgy`  
- `facing_bilingual`  
- `ane_edition`  

Maps to profile + whether tables/verse reflow rules apply. **Do this before burning conversion**, as Jacob suggested.

### Footnotes / italics / tables

1. **Anchors:** PyMuPDF span flags (`fontsize` / superscript) → insert `[^n]` before regex digit heuristics.  
2. **Bodies:** Marker `<sup>` / bottom blocks → ordered queue (pilot script).  
3. **Italics:** prefer Marker spans; VLM repair only on fail pages.  
4. **Tables:** front-matter TOC → leave as nested lists, not forced MD tables; true data tables → Marker/Surya TableRec or Docling for that page only.

### Image / staging cleanup

- Keep: final `.md`, page_map JSON, thin QA log, sha256.  
- Delete after QA: `renders/*.png`, Marker intermediate images, checkpoint blobs older than N days.  
- Add MCP/CLI flag `keep_renders=false` (default). Current `ocr_output/` already holds stray PNGs — schedule a one-time wipe of completed job dirs after MD copied to Academic Research.

## Is the pipeline still “brilliant”?

**For JSTOR merged text-layer FOTC: the full pipeline is the wrong default; Marker-only is necessary but not sufficient.** Brilliance here is the *triage + selective repair + QA gates*, which need to be finished (P0/P1), not a new mega-engine.

Estimated effort to clear FOTC integrity bar on next pilot: P0 config/profile (~1–2 h) + superscript/garbage selective repair P1 (~1–2 days coding) + second FOTC volume QA — not a months-long re-architecture.
